### 触摸启动与空闲轮询

旧实现在 15 秒无接触时轮询 74 次，74 次均返回无效数据；同一驱动随后能正确报告真实滑动。修正后区分 IRQ 触发的严格读包与超时后的补读。后者在总线读取成功、且无报点标志时返回“暂无报告”，保留上一触摸状态。复测 74 次均为暂无报告，零错误。NACK、带标志但坐标越界的报告和 IRQ 后的坏包仍按错误处理。诊断镜像在同一次运行中两次打开 GPIO 中断服务，第二次出现 IDF 的 already installed 日志；随后板级打开成功。

正式固件以 ESP-IDF 5.5.4 构建并通过镜像校验；主机回归将 11 个场景分别与原来的逐像素公式对比，每场景检查 217,156 个像素，覆盖圆环、色条、刻度、边缘和触点。复测前后用设备端摘要核对了 bootloader、分区表、完整 6 MiB factory 分区及 Flash 末尾 4 KiB，四项一致。最后复位，串口确认原来的 MotoNav 0.3.18 正常启动，ELF 标识与测试前一致。

## 实际发现并处理的问题

1. 当前终端没有激活 IDF，系统 Python 与 IDF venv 不同。工程脚本显式使用已有 venv 和工具目录，不全局安装。
2. 受限执行环境启动 GCC 时出现系统 DLL 重定位错误；在正常 Windows 执行环境检查版本成功。
3. 原中文项目路径让 GCC 无法正确读取 picolibc.specs；UTF-8设置不足以修复。
4. 单独映射盘符后使用 idf.py 仍失败，因为 idf.py 对项目路径做 realpath，还原成中文。
5. 最终方案：临时英文盘符 + 直接 CMake / Ninja 构建。所有文件仍位于用户目录，结束后通过 Unicode API 核对并移除本次映射。此路径已成功构建。
6. Chrome普通命令行窗口截图的窄窗口行为不等同于真实430px viewport；最终用独立浏览器上下文设置430px重新检查并保存截图。

失败尝试的日志保留在忽略的 `build-preparation` / `build-preparation-ascii` 中，最终产物在 `build-preparation-z`。不把失败构建当作源码错误或硬件错误。
